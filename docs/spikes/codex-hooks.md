# Spike: what Codex CLI hooks expose

Issue #69. Run on 2026-10-16 against Codex CLI 0.153.4 (macOS, arm64), through the org gateway with `gpt-6.1-sol`. Every run used a throwaway `CODEX_HOME` and a scratch project with project-level hooks (`<project>/.codex/hooks.json`). The recorder was a `sh` script that saved stdin, a redacted env, and a curl probe, then exited 0. Sanitized payloads are in [`src/hook/fixtures/codex/`](../../src/hook/fixtures/codex/).

## Payload fields

Every event carries `session_id`, `transcript_path` (always set; the rollout `.jsonl` under `$CODEX_HOME/sessions/YYYY/MM/DD/`), `cwd` and `hook_event_name`. Every event except SessionEnd also carries `model` and `permission_mode` (`default` in the TUI, `bypassPermissions` under `exec` with `approval: never`).

| Event               | Extra fields                                                                                |
| ------------------- | ------------------------------------------------------------------------------------------- |
| `SessionStart`      | `source` (`startup`, `resume`)                                                              |
| `UserPromptSubmit`  | `turn_id`, `prompt`                                                                         |
| `PreToolUse`        | `turn_id`, `tool_name`, `tool_input`, `tool_use_id`                                         |
| `PermissionRequest` | `turn_id`, `tool_name`, `tool_input` (no `tool_use_id`)                                     |
| `PostToolUse`       | `turn_id`, `tool_name`, `tool_input`, `tool_response`, `tool_use_id`                        |
| `Stop`              | `turn_id`, `stop_hook_active`, `last_assistant_message`                                     |
| `SessionEnd`        | `reason` (`other` for both an `exec` exit and a TUI `/quit`); no `model`, `permission_mode` |

`tool_name` is `Bash` for shell commands (`tool_input.command`, `tool_response` is the output string with no exit code), `view_image`, `request_user_input`, or `mcp__<server>__<tool>`. Configured but not triggered: `SubagentStart/Stop`, `PreCompact/PostCompact` and `Interrupt`.

In the TUI, SessionStart fires on the first prompt, not at launch, even though the rollout file is created at launch.

## Outputs and failures

- **additionalContext** on SessionStart, UserPromptSubmit and PostToolUse is stored in the rollout as a `developer` message. The model acts on it: a PostToolUse context asking for a closing word got that word in the final reply.
- **Timeouts:** the default is 600 s. A hook that hits its `timeout` is killed together with its children and marked `Failed`, and the turn waits for the full timeout first. SessionEnd defaults to 1 s and is clamped to 3 s, so a 1.5 s budget needs `timeout: 3` there.
- **Exit 1:** `exec` prints `hook: PostToolUse Failed` and the turn goes on. **The TUI shows it to the user** as `• Hook failed └ hook exited with code 1`.
- **Exit 2 on PostToolUse** replaces the tool result the model sees with the hook's stderr. Never use it.
- **Plain stdout on Stop** fails the hook ("hook returned invalid stop hook JSON output" in the TUI). Print JSON or nothing.
- **Latency:** inside the script (start to end, not Codex spawn to return), the `sh` recorder, which forks curl, ran at a median of 37 ms and a p95 of 42 ms (75 runs). Hooks run synchronously between steps. The end-to-end p95 that #72 checks was not measured.

## Never-block checklist

| Check                | Result for Codex                                                                                                   |
| -------------------- | ------------------------------------------------------------------------------------------------------------------ |
| Hard deadline        | Codex enforces `timeout` (and kills the hook), but the default is 600 s, so the adapter must set its own short one |
| Exit 0 on every path | Required: exit 1 is shown in the TUI, and exit 2 rewrites tool results or blocks prompts                           |
| Server down          | Unaffected: the hook reaches loopback from outside the sandbox and can fail fast                                   |
| Loop guard           | Required: `stop_hook_active` is reliable, and Codex has no cap of its own                                          |
| Valid output only    | Required: plain stdout on Stop, or additionalContext on Stop, marks the hook failed                                |

## Recommendation for the Codex adapter (#72)

1. **Ship a plugin with its own `hooks.json`, never project hooks or a shared user `hooks.json`.** Project hooks need two separate trusts and are skipped silently in `exec`. Trust in a shared file is positional, so another tool adding a hook ahead of ours untrusts it silently. A plugin's hash survives version bumps as long as the command (with `${PLUGIN_ROOT}` unexpanded) and the order stay fixed. Setup walks the user through the TUI's trust prompt once, and `golla doctor` can read `hooks.state` to tell whether every handler is trusted. Codex reads `.claude-plugin` manifests, so the plugin can share layout with the Claude Code one, but its hooks need Codex-specific outputs (see 5).
2. **Write the absolute bun path at setup.** Hooks get codex's env with no login shell, so `bun` is on PATH only by luck.
3. **Set `timeout` explicitly** (a few seconds on every event, 3 s on SessionEnd), and keep the 1.5 s internal budget.
4. **Reuse the mapping.** MCP images already parse. Add the `input_image` data-URL shape for `view_image`, sniffing the MIME type, with `tool_input.path` as the `source`. Mirror `request_user_input` from PreToolUse like `AskUserQuestion`. Take the recap from Stop `last_assistant_message`; Codex has no `turnOrigin`, so every Stop is a candidate.
5. **Feedback:** use additionalContext on PostToolUse and UserPromptSubmit. At Stop, use `decision: "block"` with the feedback as `reason`, never additionalContext. Never block when `stop_hook_active` is true.
6. **Identify the harness by the command's argument**, not by env. Never log env: it holds provider tokens.
7. **Idle wake** is not possible through hooks (`async: true` hooks cannot block and are cancelled at session end). The app-server `turn/start` path belongs to #82.

## Not tested

- How Open Design actually launches Codex. Only a hand-driven stdio app-server was tested.
- A plugin installed from a Git marketplace (only a local one was tested), and whether a plugin update that adds a hook ahead of existing ones re-prompts them.
- `async: true` hooks, the Codex desktop app, Windows, and the current Codex release (0.162.1 was available).
